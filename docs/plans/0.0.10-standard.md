# 0.0.10: kitchen follows the standard (Phase 2 runbook)

*Written 2026-11-26 for next week, at a computer. Phase 2 of the
[roadmap](../../standard/roadmap.md): kitchen restructured into contract, runtime and interface
([architecture](../../standard/architecture.md)), released as 0.0.10. No app changes in this phase
([0.0.10-gaps.md](0.0.10-gaps.md) says what they will need). MCP comes last.*

## Rules for every pull request

- One pull request per step below, built and tested with `scripts/check-all.sh` (stages A–C in CI;
  stage D on a GPU machine before the release).
- A move is never in the same diff as a change of behaviour: reviewers read moves with
  `git diff -M` and see nothing else.
- Every change to the contract changes `standard/spec/` in the same pull request.
- Library upgrades (standalone GPUI, CubeCL 0.12 / Burn 0.23) land between steps, never inside one
  ([upcoming-upgrades.md](upcoming-upgrades.md)).

## Until 0.0.10, for new kitchen code

From the note kept on the old `docs/strata` branch, still true until the layers exist:

- Name results and code by content ID where content matters.
- Record who ran something and through what (a person; an app, an interface or an agent).
- Keep back-end logic out of interface crates; if a widget needs data, it asks a view-model.
- Keep the standard's working name out of code that is costly to rename: modules are named for
  what they do.

## Step 2: the contract crate

`contract/kitchen-contract`, depending on nothing of ours (serde, schemars only):

- **Types** ([§1](../../standard/spec/01-types.md)): `Type` (shared names and `<ns>:<name>`),
  `Format`, matching. From kitchen-pipeline's `PortType` and kitchen-artifacts' `ArtifactKind`,
  merged: one type system.
- **Steps** ([§2](../../standard/spec/02-ops.md)): the step description (ports, params with
  kinds and ranges, `margin`, `source`: built in, script, tool, composite; `finish` and
  `available`, decision 0015). From kitchen-pipeline's `OpSpec` and kitchen-tool's `Operation`.
- **Results and run records** ([§3](../../standard/spec/03-results.md)): content IDs (JCS + SHA-256,
  decision 0003), run records, run keys. From kitchen-artifacts' `identity`, `provenance`, `run_key`.
- **Pipelines** ([§4](../../standard/spec/04-pipelines.md)): sources, nodes, edges, outputs; the
  check (types, cycles, margins). From kitchen-pipeline's `graph`.
- **Confirmation** ([§5](../../standard/spec/05-confirmation.md)): states and records.
- **One version** ([§7](../../standard/spec/07-versioning.md)): `CONTRACT_VERSION`, written into
  every document.
- **Schemas:** generated into `standard/schemas/`, with the test that fails when they are stale.
- **Examples as tests:** examples 01–04 as fixtures (pipelines, records) the contract crate parses
  and checks; hard cases A–E become runtime tests in step 5.
- **Done when:** kitchen-pipeline and kitchen-artifacts use `kitchen-contract`'s types and keep
  only what runs (no second definition of a type, a step, a record or a pipeline anywhere).

## Step 3: the runtime takes the back end

- `runtime/kitchen-engine` ← kitchen-pipeline's `engine` and `domain` (the walk: pieces, margins,
  `finish`; windows with read-ahead for dsp-kitchen, tiles at a level for lucem, one piece for
  garnish).
- `runtime/kitchen-scripts` ← kitchen-pipeline's `script/` (read, check, confirm, warm workers) and
  kitchen-code's `run` (script running leaves the editor). Brings in lucem's warm Python pool and
  `uv` environments as the design to follow (gaps doc).
- `runtime/kitchen-store` ← kitchen-artifacts (what is left after step 2): results by content ID, run
  records, run keys, a folder + SQLite store; results kept by reference for huge files (gap 2).
- `runtime/kitchen-services` ← kitchen-shell's `jobs`, `activity`, `env`, `changes` (their models;
  the frame keeps drawing them).
- `runtime/kitchen-tools` ← kitchen-plugin + kitchen-tool, one protocol (describe / validate / run,
  install for tool steps: gap 7).
- **Done when:** `check-layers` has no exception left for the interface reaching back-end logic;
  every interface crate draws state it gets from the runtime.

## Step 4: the runtime API (client, store, server)

- `runtime/kitchen-client`: the calls of [§6.1](../../standard/spec/06-runtime-api.md) as a Rust
  trait, implemented in-process first. View-models (and the Python package) only use this.
- `runtime/kitchen-server`: the same calls over HTTP and stdio (JSON lines), on kitchen-network
  for who may connect.
- **Python:** `python/` gets the decorators (`@op`) and the client, for scripts and notebooks.
- **MCP joins last:** the server's third transport; kitchen-chat then talks to the runtime through
  the client, and the MCP host leaves the chat panel.
- **Done when:** a test, a Python script and (once MCP is in) an agent run example 01 through the
  same calls; hard cases A–C pass on stand-in domains (a windowed signal and a tiled image).

## Decided

- **The structure and names are approved (2026-11-26):** the folders contract / runtime /
  interface, the renames of step 1 (`kitchen-network`, `kitchen-downloads`, `kitchen-editor`,
  `kitchen-chat`), and the crates of steps 2–4 (`kitchen-contract`, `kitchen-engine`,
  `kitchen-scripts`, `kitchen-store`, `kitchen-services`, `kitchen-tools`, `kitchen-client`,
  `kitchen-server`). Apps then keep only `domain/` and `app/` (view-models, views): their own
  pipeline, session, server, command line and MCP crates go away.
- **Published crates keep their names** (`kitchen-ui`, `kitchen-views`, `kitchen-shell`) until
  the public name (decision 0007).
- **kitchen-ui is not split** into theme and widgets in 0.0.10 unless step 3 needs it.
