# 0.0.10: kitchen follows the standard (Phase 2 runbook)

*Written 2026-11-26 for next week, at a computer. Phase 2 of the
[roadmap](../../standard/roadmap.md): kitchen restructured into contract, runtime and interface
([architecture](../../standard/architecture.md)), released as 0.0.10. No app changes in this phase
([0.0.10-gaps.md](0.0.10-gaps.md) says what they will need). MCP comes last.*

## Rules for every pull request

- One pull request per step below, built and tested with `scripts/check-all.sh` (stages A–C in CI;
  stage D on a GPU machine before the release).
- A move is never in the same diff as a change of behaviour: reviewers read moves with
  `git diff -M` and see nothing else.
- Every change to the contract changes `standard/spec/` in the same pull request.
- Library upgrades (standalone GPUI, CubeCL 0.12 / Burn 0.23) land between steps, never inside one
  ([upcoming-upgrades.md](upcoming-upgrades.md)).

## Until 0.0.10, for new kitchen code

From the note kept on the old `docs/strata` branch, still true until the layers exist:

- Name results and code by content ID where content matters.
- Record who ran something and through what (a person; an app, an interface or an agent).
- Keep back-end logic out of interface crates; if a widget needs data, it asks a view-model.
- Keep the standard's working name out of code that is costly to rename: modules are named for
  what they do.

## Step 2: the contract crate (done)

`contract/kitchen-contract`, depending on nothing of ours (serde, schemars only):

- **Types** ([§1](../../standard/spec/01-types.md)): `Type` (shared names and `<ns>:<name>`),
  `Format`, matching. From kitchen-pipeline's `PortType` and kitchen-artifacts' `ArtifactKind`,
  merged: one type system.
- **Steps** ([§2](../../standard/spec/02-ops.md)): the step description (ports, params with
  kinds and ranges, `margin`, `source`: built in, script, tool, composite; `finish` and
  `available`, decision 0015). From kitchen-pipeline's `OpSpec` and kitchen-tool's `Operation`.
- **Results and run records** ([§3](../../standard/spec/03-results.md)): content IDs (JCS + SHA-256,
  decision 0003), run records, run keys. From kitchen-artifacts' `identity`, `provenance`, `run_key`.
- **Pipelines** ([§4](../../standard/spec/04-pipelines.md)): sources, nodes, edges, outputs; the
  check (types, cycles, margins). From kitchen-pipeline's `graph`.
- **Confirmation** ([§5](../../standard/spec/05-confirmation.md)): states and records.
- **One version** ([§7](../../standard/spec/07-versioning.md)): `CONTRACT_VERSION`, written into
  every document.
- **Schemas:** generated into `standard/schemas/`, with the test that fails when they are stale.
- **Examples as tests:** examples 01–04 as fixtures (pipelines, records) the contract crate parses
  and checks; hard cases A–E become runtime tests in step 5.
- **Done when:** kitchen-pipeline and kitchen-artifacts use `kitchen-contract`'s types and keep
  only what runs (no second definition of a type, a step, a record or a pipeline anywhere).

**Done 2026-11-27.** Left for step 3, where they become runtime code: artifact kinds still name
the tools' ports (read as type and format with `types::from_kind`), and kitchen-artifacts'
`Provenance` (a tool run's record written next to its output) gives way to the contract's
`RunRecord` when the store is built. The script review still speaks of confirmation; it follows
decision 0016 (checked is enough until v0.2) when scripts move to `runtime/kitchen-scripts`.

## Step 3: the runtime takes the back end

In four pull requests, as planned on 2026-11-27: **3a** engine and scripts, **3b** the store
(run records as JSON files in the workspace's `.<app>/runs/`; SQLite only on the orchestrator),
**3c** services, **3d** tools (kitchen-plugin and kitchen-tool merged, ports as type and format,
the plugin Settings page to kitchen-shell, no layer exception left). **All done 2026-11-27.**

- `runtime/kitchen-engine` ← kitchen-pipeline's `engine` and `domain` (the walk: pieces, margins,
  `finish`; windows with read-ahead for dsp-kitchen, tiles at a level for lucem, one piece for
  garnish).
- `runtime/kitchen-scripts` ← kitchen-pipeline's `script/` (read, check, confirm, warm workers) and
  kitchen-code's `run` (script running leaves the editor). Brings in lucem's warm Python pool and
  `uv` environments as the design to follow (gaps doc).
- `runtime/kitchen-store` ← kitchen-artifacts (what is left after step 2): results by content ID, run
  records, run keys, a folder + SQLite store; results kept by reference for huge files (gap 2).
- `runtime/kitchen-services` ← kitchen-shell's `jobs`, `activity`, `env`, `changes` (their models;
  the frame keeps drawing them).
- `runtime/kitchen-tools` ← kitchen-plugin + kitchen-tool, one protocol (describe / validate / run,
  install for tool steps: gap 7).
- **Done when:** `check-layers` has no exception left for the interface reaching back-end logic;
  every interface crate draws state it gets from the runtime.

## Step 4: the runtime API (decision 0017)

The calls of [§6.1](../../standard/spec/06-runtime-api.md), defined once in protobuf, carried over
WebTransport (HTTP/3) with Connect as the TCP fallback. Built on what dsp-kitchen and lucem already
do (sources in the decision); MCP last.

| Part | Crate or file | From |
|---|---|---|
| **4.0** TOML documents for every app | `kitchen-contract::documents` | dsp-kitchen's `PipelineSpec::load` |
| **4a** the client: the calls as a Rust trait (async and blocking forms), the in-process runtime | `runtime/kitchen-client` | dspk-stream's `Link` |
| **4b** `runtime.proto` and the codec: framing, JSON documents, Arrow tables, raw array chunks; round trips; `buf breaking` in CI | `contract/proto/kitchen/runtime/v1/`, `runtime/kitchen-wire` | dspk-stream's protocol and framing |
| **4c** the server on WebTransport over HTTP/3: a stream per call, data on its own streams, compute pool, priorities, cancel on reset; pairing and mutual TLS | `runtime/kitchen-server` | lucem-stream's WebTransport, dspk-stream's sessions, kitchen-network |
| **4d** Connect, gRPC and gRPC-Web on TCP from the same `.proto` (tonic as plan B) | `runtime/kitchen-server` | new |
| **4e** stored results by range reads (Zarr v3 shards) | `runtime/kitchen-server` | lucem's OME-Zarr reading |
| **4f** MCP over the same calls (**deferred, 2026-11-27:** after the tools' migration and the garnish and orchestrate releases); kitchen-chat talks to the runtime through the client | `runtime/kitchen-server`, `interface/kitchen-chat` | lucem-mcp |
| browser | the client's WebTransport link in WebAssembly; two builds (threads or not); the engine in a worker owning the GPU; OffscreenCanvas | `kitchen-client` | dspk-engine-web, lucem-engine-web, the isolation service worker |

**4.0 and 4a–4e done 2026-11-27** (WebTransport with tokens and pairing; mutual
TLS for computers holding a certificate, priorities and data on streams of their own come with 4e;
4d answers Connect, gRPC and gRPC-Web by hand on hyper, one unary method, so tonic was not needed;
checked from Python's grpcio; mutual TLS, pairing over HTTP and stream priorities followed; 4e reads regions of stored Zarr arrays with zarrs as calls of their
own, `result.array` and `result.range`, answered as one chunk each on every transport).

**The browser side (planned and done 2026-11-27; the threads build is not tested yet)**, from lucem's `web_client` and dsp-kitchen's
`dspk-engine-web`, in `runtime/kitchen-web` (WebAssembly only; empty elsewhere):

1. **The page's link:** `PageLink`, a `Runtime` for a page. WebTransport through a few lines of
   JavaScript (`web/kitchen-transport.js`, as lucem keeps off web-sys's unstable bindings), a
   stream per call, the server's certificate by its hash; Connect over `fetch` where UDP is
   blocked (the server has no WebSocket: Connect is the TCP fallback). Pairing on both. Awaited on
   the page's main thread (`call_async`), waited for from a worker in a build with threads.
2. **The engine worker:** an app's own `Runtime` answering the same protobuf calls in a module
   worker (`web/engine-worker.js`), for a page no server serves; it owns the GPU, and takes an
   `OffscreenCanvas` the page hands it. `start_worker` gives the page the same `PageLink`.
3. **Two builds:** with threads (shared memory: the page served cross-origin isolated, the
   isolation service worker `web/isolate-sw.js` where headers cannot be set) and without.
4. **Tested in a browser:** headless Chromium runs a test page against `kitchen-server`: pairs,
   lists, runs, reads a region, over WebTransport and then over Connect.

- **Done when:** a test, a Python notebook (gRPC) and, once MCP is in, an agent run example 01
  through the same calls; a page and a desktop client read a tiled image and a windowed signal from
  the same server over WebTransport; hard cases A–C pass on stand-in domains.
