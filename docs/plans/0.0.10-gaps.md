# What lucem and dsp-kitchen have, and where it lands

*Read 2026-11-26, without changing either: lucem 0.0.6 (`93d9488`), dsp-kitchen 0.0.13 (`eba2720`).
Input to the Phase 2 runbook ([0.0.10-standard.md](0.0.10-standard.md)) and to the open questions of
the [standard](../../standard/README.md).*

Each row is something an app does today, the layer it moves to ([architecture](../../standard/architecture.md)):
**contract**, **runtime**, **interface**, or the app's **domain**, and whether the spec already
covers it (✓), covers it partly (◐), or not at all (✗, a gap listed at the end).

## Gaps: questions for the standard

Each needs a decision before Phase 2's third step (merging the contract). A recommendation follows
each.

1. **Batch runs.** dsp-kitchen runs one pipeline over a glob or a list, and reads several
   recordings as one (merge). The runtime API's `run` takes one filling of the sources.
   *Recommend:* `run` takes a list of fillings and returns one run per filling, grouped under a
   batch ID; a merge is a source description of the domain (several files read as one), not a
   contract notion.
2. **Writing to a chosen path.** Both apps write outputs where the user asks (`{stem}.zarr`). The
   spec keeps results in the store by content ID. *Recommend:* results always go to the store; a
   path is an `export` of a result (the file plus its record next to it). Huge results are kept by
   reference (§3.6), so exporting a 250 GB recording is not a copy.
3. **Work after the last piece.** Hard case B names a domain `finish` (lucem's stitching).
   *Recommend:* a step may declare `finish` in its description (joins its pieces' outputs); the
   engine calls it once after the walk; a step without it has outputs concatenated in piece order.
4. **Execution settings.** Device, piece size, read-ahead, threads, upload mode: dsp-kitchen keeps
   them in the pipeline, lucem in run options. *Recommend:* never in the pipeline (it must run
   anywhere); options of `run`, written into the run record's `environment`, and left out of the
   run key (they change speed, not results).
5. **Live sources.** dsp-kitchen's devices run a chain over an unbounded stream with taps and
   viewers. *Recommend:* out of the contract's first version; a capability (`live`) in the
   handshake later. The chain is still checked by `pipeline.check` (dspk's `Purpose::Live`).
6. **Viewing large results.** Tiles of a slide, envelopes of a recording: `result.read` returns
   bytes or a handle. *Recommend:* `result.read` takes a region (tile, window, level) for array
   types, answered by the domain's reader; envelopes and pyramids stay domain messages over
   kitchen-net, as today.
7. **Steps that are not installed.** A model plugin may lack its weights or runtime.
   *Recommend:* a step description carries `available` (and why not: "weights not downloaded"),
   and `step.install` joins the API for tool steps.
8. **Performance in run records.** dsp-kitchen records bytes moved and time per stage.
   *Recommend:* an optional `metrics` object in the run record, never part of the run key.
9. **Pyramid levels.** lucem runs at a level of the pyramid and previews at a coarser one.
   *Recommend:* the level is a property of the source filling (which level is read), so a run at a
   level is recorded as such; a preview may ask for a coarser level.
10. **Display nodes.** Both graphs hold View nodes (what Explore draws, its style).
    *Recommend:* not in the pipeline; a view-model names a pipeline output and how to draw it.

## Phase 2 notes from this reading

- kitchen-pipeline's `Domain` must carry both walks above: windows with read-ahead and a writer
  thread (dspk), tiles at a level with planes or volumes and a stitching `finish` (lucem).
- The warm Python worker pool and `uv` environments in lucem's app belong in `runtime/scripts`.
- dspk's chain planning per purpose (preview, batch, live) with refusals is the best model for
  `pipeline.check`.
- Neither app is changed in Phase 2. They move in phases 5 and 6, onto 0.0.10 or later.
